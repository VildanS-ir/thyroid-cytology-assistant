# Первичная разметка медицинского датасета

## Назначение

Скрипт `src/common/annotate_dataset.py` выполняет воспроизводимую первичную обработку двух исходных Excel-таблиц и формирует единый master-датасет:

`data/processed/annotated_dataset.csv`

Это этап **аннотирования (разметки)**, а не окончательной очистки для обучения. Скрипт сохраняет все исходные записи, их происхождение, извлекает категории Bethesda, выявляет потенциально проблемные случаи, размечает дубликаты и сохраняет воспроизводимую версию датасета.

Строки с ошибками, пропусками, утечкой целевой переменной или дубликатами автоматически не удаляются. Поэтому название `annotated_dataset.csv` описывает фактическое содержание файла точнее, чем прежнее `cleaned_dataset.csv`.

---

## Входные данные

Скрипт использует два исходных файла:

- `data/raw/cytology_data_1.xlsx`
- `data/raw/cytology_data_2.xlsx`

Для каждого исходного файла рассчитываются:

- общее количество строк;
- количество заполненных значений по каждому столбцу;
- количество пропусков по каждому столбцу;
- количество полностью заполненных строк.

Пустым считается значение, если оно является:

- `NaN`;
- пустой строкой `""`;
- строкой, содержащей только пробелы.

---

## Выходной датасет

Итоговый `annotated_dataset.csv` содержит следующие поля:

| Поле | Назначение |
|---|---|
| `case_id` | Стабильный технический идентификатор записи |
| `source_table` | Имя исходного Excel-файла |
| `source_row` | Номер строки в исходном Excel-файле |
| `description` | Цитологическое описание. Единственное текстовое поле, которое в дальнейшем может использоваться классификатором |
| `conclusion` | Исходное заключение. Используется для получения целевой категории, но не подаётся на вход классификатора |
| `bethesda` | Категория Bethesda, извлечённая из `conclusion` |
| `needs_review` | Требуется ли ручная проверка записи |
| `review_reason` | Причина или несколько причин ручной проверки |
| `target_leakage` | Содержится ли прямое указание Bethesda в `description` |
| `description_in_conclusion` | Есть ли признаки того, что описательная часть могла находиться в `conclusion` |
| `duplicate_group` | Идентификатор группы дубликатов |
| `duplicate_type` | Тип найденного дубликата |

---

## Связь записей с исходными таблицами

Одна из задач разметки - сохранить возможность однозначно определить, из какого исходного файла и из какой строки была получена каждая запись.

Для этого используются три поля:

- `case_id`
- `source_table`
- `source_row`

### `case_id`

`case_id` - стабильный технический идентификатор записи.

Используется следующий формат:

- `T1_000001` - первая запись из первой исходной таблицы;
- `T1_000002` - вторая запись из первой исходной таблицы;
- `T2_000001` - первая запись из второй исходной таблицы.

Префикс:

- `T1` соответствует `cytology_data_1.xlsx`;
- `T2` соответствует `cytology_data_2.xlsx`.

После дальнейшей обработки и фильтрации `case_id` не перенумеровывается.

Это позволяет сохранять идентичность записи между разными версиями датасета.

### `source_table`

`source_table` содержит имя исходного файла, из которого получена запись.

В текущем наборе данных используются:

```text
cytology_data_1.xlsx
cytology_data_2.xlsx
```

Пример:

```text
case_id       source_table
T1_000001     cytology_data_1.xlsx
T2_000001     cytology_data_2.xlsx
```

### `source_row`

`source_row` содержит номер строки в исходном Excel-файле.

Это именно номер строки Excel, а не индекс pandas и не порядковый номер строки в `annotated_dataset.csv`.

В первой исходной таблице используется:

```python
header=[7, 8]
```

Поэтому первая строка данных соответствует Excel-строке 10:

```text
T1_000001 -> Excel-строка 10
T1_000002 -> Excel-строка 11
T1_000003 -> Excel-строка 12
```

Во второй исходной таблице используется:

```python
header=5
```

Поэтому первая строка данных соответствует Excel-строке 7:

```text
T2_000001 -> Excel-строка 7
T2_000002 -> Excel-строка 8
T2_000003 -> Excel-строка 9
```

Пример итоговой связи:

| case_id | source_table | source_row |
|---|---|---:|
| `T1_000001` | `cytology_data_1.xlsx` | 10 |
| `T1_000002` | `cytology_data_1.xlsx` | 11 |
| `T2_000001` | `cytology_data_2.xlsx` | 7 |

Если при ручной проверке обнаружена проблема, например у записи `T1_000127`, и указано:

```text
source_table = cytology_data_1.xlsx
source_row = 136
```

то для проверки исходной информации необходимо открыть файл `cytology_data_1.xlsx` и перейти к Excel-строке 136.

Поля `source_table` и `source_row`:

- не подаются в модель;
- не используются как признаки;
- не изменяют медицинский текст;
- нужны для трассировки происхождения данных;
- используются при ручной проверке и анализе ошибок.

Исходные Excel-файлы находятся локально в:

```text
data/raw/
```

и не должны публиковаться в Git.

## Извлечение Bethesda

Категория Bethesda извлекается только из поля `conclusion`.

Поддерживаются категории:

`I`, `II`, `III`, `IV`, `V`, `VI`.

Учитываются различные варианты записи, например:

- `Bethesda II`;
- `Bethesda-II`;
- `Bethesda: II`;
- `Bethesda: диагностическая категория VI`;
- `IV диагностическая категория`;
- варианты слова Bethesda со смешанными латинскими и кириллическими символами.

Например:

`Вethesda`, `Bеthesda`, `Bethеsda`, `Bethesdа`.

Если обнаружена одна категория:

```text
II
```

она записывается как одно значение.

Если обнаружено несколько разных категорий:

```text
II, IV
```

сохраняются все найденные категории.

Автоматически выбирать первую, последнюю или максимальную категорию запрещено.

Такая запись помечается для ручной проверки.

---

## Принцип `target_leakage`

Поле `description` является будущим входом классификатора.

Поэтому прямое указание категории Bethesda внутри `description` является потенциальной утечкой целевой переменной.

Пример:

```text
... соответствует Bethesda IV ...
```

Для такой записи устанавливается:

```text
target_leakage = True
needs_review = True
review_reason = target_leakage
```

Исходный текст при этом не изменяется.

Фразу Bethesda автоматически удалять из `description` нельзя.

До ручной проверки такие записи не должны использоваться в train/test.

---

## Описание внутри `conclusion`

Некоторые записи могут не иметь нормального `description`, при этом часть описательного текста может находиться в `conclusion`.

Скрипт выполняет только консервативный поиск таких случаев и устанавливает:

```text
description_in_conclusion = True
```

Для поиска используются характерные признаки описательной части, например:

- `в мазке`;
- `пунктирован`.

Автоматического переноса текста из `conclusion` в `description` не выполняется.

Исходные поля никогда не перезаписываются.

Такие записи должны быть рассмотрены отдельно.

---

## Работа с дубликатами

Дубликаты в `annotated_dataset.csv` автоматически не удаляются.

Каждая исходная запись сохраняется, даже если её текст полностью или почти полностью совпадает с другой записью.

Это необходимо для сохранения происхождения данных и возможности проверить, из каких исходных строк возникли совпадения.

Для разметки используются два поля:

- `duplicate_group`
- `duplicate_type`

---

## Что сравнивается

Для определения дубликатов используется одновременно пара:

```text
description + conclusion
```

То есть совпадение только одного `description` или только одного `conclusion` на этом этапе не означает, что строки являются полными дубликатами.

Например:

```text
Запись A:
description = "Описание 1"
conclusion  = "Bethesda II"

Запись B:
description = "Описание 1"
conclusion  = "Bethesda III"
```

не являются одной duplicate-группой, потому что заключения различаются.

А:

```text
Запись A:
description = "Описание 1"
conclusion  = "Bethesda II"

Запись B:
description = "Описание 1"
conclusion  = "Bethesda II"
```

являются дубликатами.

---

## Technical duplicate

`duplicate_type = technical`

означает, что значения `description` и `conclusion` в исходных записях буквально совпадают.

Пример:

```text
T1_000100

description:
"В мазке обнаружены клетки..."

conclusion:
"Bethesda II"
```

и:

```text
T1_004500

description:
"В мазке обнаружены клетки..."

conclusion:
"Bethesda II"
```

Такие записи получают одну группу:

```text
case_id       duplicate_group    duplicate_type
T1_000100     DUP_000001         technical
T1_004500     DUP_000001         technical
```

Обе строки остаются в `annotated_dataset.csv`.

---

## Text duplicate

`duplicate_type = text`

означает, что исходные значения отличаются, но становятся одинаковыми после безопасной технической нормализации.

Например:

```text
"В мазке обнаружены клетки..."
```

и:

```text
"  В мазке   обнаружены клетки... "
```

визуально представляют один текст, хотя исходные строки технически различаются.

### Нормализация включает

1. Unicode-нормализацию:

```python
unicodedata.normalize("NFKC", text)
```

2. Замену неразрывного пробела обычным пробелом.

3. Приведение нескольких пробелов и переносов строк к одному пробелу.

Например:

```text
"В мазке

обнаружены   клетки"
```

превращается в:

```text
"В мазке обнаружены клетки"
```

4. Приведение текста к единому регистру с помощью `casefold()`.

Например:

```text
"В МАЗКЕ обнаружены клетки"
```

и:

```text
"в мазке обнаружены клетки"
```

считаются одинаковыми после нормализации.

### Что при нормализации не изменяется

Для предотвращения ошибочного объединения медицински разных записей скрипт не удаляет:

- слова;
- числа;
- римские числа;
- медицинские обозначения;
- диагнозы;
- категории Bethesda;
- пунктуацию;
- части текста.

Также не используется:

- fuzzy matching;
- расстояние Левенштейна;
- embeddings;
- семантическая близость;
- автоматическое исправление опечаток.

То есть `text duplicate` означает только очень близкое техническое совпадение текстов, а не предполагаемое смысловое сходство.

---

## Формирование duplicate-группы

Сначала для каждой строки создаётся нормализованная пара:

```text
normalized(description)
+
normalized(conclusion)
```

Если одна и та же нормализованная пара встречается не менее двух раз, такие записи образуют одну duplicate-группу.

Группы получают последовательные идентификаторы:

```text
DUP_000001
DUP_000002
DUP_000003
...
```

Пример:

```text
case_id       duplicate_group    duplicate_type
T1_000100     DUP_000001         technical
T1_004500     DUP_000001         technical

T1_001200     DUP_000002         text
T2_000230     DUP_000002         text
```

У записей, для которых совпадений не найдено:

```text
duplicate_group = пусто
duplicate_type  = пусто
```

---

## Как определяется тип всей группы

После формирования группы сравниваются исходные, ненормализованные пары `description + conclusion`.

Если все записи группы имеют одну и ту же исходную пару, группа получает:

```text
duplicate_type = technical
```

Если хотя бы одна запись отличается от остальных в исходном виде, но после нормализации относится к той же группе:

```text
duplicate_type = text
```

Пример:

```text
A:
"В мазке обнаружены клетки..."

B:
"В мазке обнаружены клетки..."

C:
" В мазке   обнаружены клетки... "
```

После нормализации все три записи совпадают.

При этом A и B являются буквальными копиями, а C отличается техническим оформлением.

Вся группа получает:

```text
duplicate_type = text
```

поскольку внутри группы существуют разные исходные варианты текста.

---

## Что происходит с дубликатами после обнаружения

На этапе формирования `annotated_dataset.csv` ничего не удаляется.

Например, если исходные данные содержат:

```text
T1_000100
T1_004500
T2_000230
```

и все три записи попали в:

```text
DUP_000017
```

в master-датасете сохраняются все три записи вместе с их:

- `case_id`;
- `source_table`;
- `source_row`;
- исходным `description`;
- исходным `conclusion`.

Это позволяет определить, были ли одинаковые тексты получены:

- из одной исходной таблицы;
- из разных таблиц;
- из разных строк одного файла.

---

## Использование дубликатов при обучении

Сохранение всех дубликатов в master-датасете не означает, что все они должны использоваться для обучения модели.

При формировании обучающего датасета допускается выбрать одного представителя duplicate-группы.

Например:

```text
DUP_000017:
T1_000100
T1_004500
T2_000230
```

в `annotated_dataset.csv` сохраняются все три записи.

В обучающую выборку может быть взята только одна из них.

При этом необходимо соблюдать отдельное правило:

**одинаковые `description` не должны одновременно попадать в train и test.**

Это правило действует даже в случаях, когда строки не являются полными дубликатами по паре `description + conclusion`.

Поэтому перед разделением данных на train/test необходимо отдельно контролировать группы одинаковых нормализованных `description`.

Если в будущем появится `patient_id`, записи одного пациента также не должны одновременно попадать в train и test.

---

## Почему дубликаты не удаляются на этапе разметки

Автоматическое удаление дубликатов на этапе первичной очистки привело бы к потере информации о происхождении данных.

Например, две одинаковые записи могут находиться:

```text
cytology_data_1.xlsx, строка 150
cytology_data_2.xlsx, строка 83
```

Если сразу оставить только первую запись, информация о наличии того же текста во втором источнике будет потеряна.

Поэтому применяется двухэтапный подход:

```text
Исходные Excel
        ↓
annotated_dataset.csv
        ↓
все записи сохранены
дубликаты только размечены
        ↓
dataset_first.csv (текущее название)
        ↓
выбираются записи, допустимые для классификации
        ↓
train / test
```

Таким образом:

- `annotated_dataset.csv` сохраняет полную историю данных;
- `duplicate_group` показывает связанные записи;
- `duplicate_type` показывает характер совпадения;
- `source_table` и `source_row` позволяют вернуться к оригиналу;
- удаление или выбор одного представителя выполняется только при подготовке конкретного датасета для модели.

---

## `needs_review`

`needs_review = True` означает, что запись требует ручной проверки.

Причины сохраняются отдельно в `review_reason`.

Используются следующие значения:

- `missing_description` - отсутствует описание;
- `bethesda_not_found` - категория Bethesda не найдена;
- `multiple_bethesda` - найдено несколько категорий;
- `target_leakage` - категория Bethesda обнаружена в `description`;
- `description_in_conclusion` - предполагаемая описательная часть находится в `conclusion`.

Если одновременно обнаружено несколько проблем, причины записываются через `;`.

Пример:

```text
missing_description; description_in_conclusion
```

Таким образом, `needs_review` показывает сам факт проблемы, а `review_reason` позволяет определить её причину.

---

## Основной принцип первичной разметки

`annotated_dataset.csv` является master-датасетом.

На этапе первичной разметки записи не удаляются, даже если они:

- являются дубликатами;
- не содержат `description`;
- не имеют распознанной Bethesda;
- содержат несколько категорий;
- имеют потенциальную утечку целевой переменной;
- требуют ручной проверки.

Вместо удаления используются дополнительные флаги и служебные поля.

Отдельный датасет для классификации формируется на следующем этапе обработки. Именно там выполняются фильтрация и отбор записей. Текущий скрипт не выполняет эту очистку.

---

## Запуск скрипта

Из корня репозитория с активным виртуальным окружением:

```bash
python -m src.common.annotate_dataset
```

При успешном выполнении скрипт сохраняет `data/processed/annotated_dataset.csv`, вычисляет SHA256 и создаёт версионную копию в `data/processed/versions/`.

## Версионирование

После сохранения:

```text
data/processed/annotated_dataset.csv
```

для файла рассчитывается полный SHA256-хеш.

Дополнительно создаётся неизменяемая версия:

```text
data/processed/versions/
annotated_dataset_<12 символов SHA256>.csv
```

Например:

```text
annotated_dataset_a81c52f19e42.csv
```

Для этого используется модуль:

```text
src/common/dataset_versioning.py
```

Основные функции:

```python
calculate_sha256(file_path)
save_dataset_version(dataset_path)
```

Полный SHA256 используется как версия датасета при логировании экспериментов в MLflow.

Если содержимое датасета изменится, изменится и его SHA256.

Если содержимое полностью совпадает с уже сохранённой версией, повторная копия не создаётся.

---

## Передача данных на этап классификации

При построении классификатора:

- вход модели - только `description`;
- `conclusion` не используется как признак;
- `bethesda` используется как целевая категория;
- записи с отсутствующим `description` исключаются из обучения;
- записи с несколькими Bethesda исключаются до ручной проверки;
- записи с `target_leakage=True` исключаются до ручной проверки;
- одинаковые описания не должны одновременно находиться в train и test;
- при наличии `patient_id` записи одного пациента также не должны распределяться между train и test.

Фильтрация для обучения выполняется отдельным скриптом и не должна изменять master-датасет. Название и итоговый формат второго этапа будут зафиксированы при его переименовании; до этого существующий `dataset_first.csv` сохраняет историческое название.

---

## Ручная проверка

Для ручной проверки должна формироваться отдельная стратифицированная выборка из 50 записей.

Целевая структура:

- 20 обычных записей;
- 10 записей без `description`;
- 10 неоднозначных записей или записей с несколькими Bethesda;
- 5 записей с `target_leakage=True`;
- 5 текстовых дубликатов.

Если в какой-либо категории недостаточно записей, количество перераспределяется между другими группами.

Для воспроизводимости используется:

```python
random_state=42
```

Для каждой выбранной записи необходимо сохранять:

- исходные поля;
- `case_id`;
- `source_table`;
- `source_row`;
- результат автоматической обработки;
- обнаруженные проблемы;
- результат ручной проверки.
