# Подготовка общего рабочего датасета

## 1. Назначение

Скрипт `src/common/prepare_dataset.py` выполняет второй этап обработки медицинских данных: **отбор и подготовку записей из ранее размеченного master-датасета**.

Входной файл:

```text
data/processed/annotated_dataset.csv
```

Выходные файлы:

```text
data/processed/prepared_dataset.csv
data/processed/short_descriptions_review.csv
```

`prepared_dataset.csv` планируется использовать как общий исходный корпус для двух задач дипломного проекта:

- многоклассовая классификация цитологических заключений по Bethesda;
- поиск похожих цитологических описаний.

---

## 2. Место в конвейере обработки

```text
data/raw/cytology_data_1.xlsx
data/raw/cytology_data_2.xlsx
           |
           v
src/common/annotate_dataset.py
           |
           v
data/processed/annotated_dataset.csv
  Все исходные записи сохранены.
  Проставлены Bethesda, needs_review,
  target_leakage и группы дубликатов.
           |
           v
src/common/prepare_dataset.py
           |
           +--> фильтрация непригодных записей
           |
           +--> выбор одного представителя duplicate-группы
           |
           +--> проверка коротких description по P5
           |
           +-------------------------------+
           |                               |
           v                               v
prepared_dataset.csv       short_descriptions_review.csv
           |                               |
           v                               v
классификация / поиск         отдельная ручная проверка
```

**Разметка и подготовка - разные операции.** `annotate_dataset.py` не удаляет дубликаты или проблемные записи; `prepare_dataset.py` отбирает рабочее подмножество по уже выставленным признакам.

---

## 3. Входные данные и зависимости

### 3.1. Основной входной файл

Скрипт читает:

```text
data/processed/annotated_dataset.csv
```

Этот файл формирует `src/common/annotate_dataset.py`. Исходные Excel-файлы напрямую в `prepare_dataset.py` не читаются.

Если `annotated_dataset.csv` отсутствует, `prepare_dataset.py` **запускает функцию `main()` из `annotate_dataset.py`** и тем самым сначала создаёт master-датасет.

Если файл существует, он используется **как есть**: скрипт не проверяет, изменились ли исходные Excel или правила аннотирования. Для обновления разметки нужно отдельно повторно запустить `annotate_dataset.py`.

### 3.2. Обязательные столбцы

Перед обработкой проверяется наличие следующих полей:

| Поле | Для чего используется |
|---|---|
| `case_id` | Стабильный идентификатор записи |
| `source_table` | Исходный Excel-файл |
| `source_row` | Номер строки в исходном Excel |
| `description` | Проверка наличия и длины описания; основной текст для моделей |
| `conclusion` | Заключение, сохранённое для анализа и поиска |
| `bethesda` | Проверка наличия одной корректной категории |
| `duplicate_group` | Выбор одного представителя группы дубликатов |
| `duplicate_type` | Сохранение типа дубликата |
| `needs_review` | Исключение записей, требующих ручной проверки |
| `target_leakage` | Исключение записей с потенциальной утечкой категории |

Входной датасет может содержать и дополнительные поля. Они не участвуют во всех проверках и не обязательно сохраняются на выходе.

Если хотя бы одного обязательного столбца нет, выполнение прекращается с `ValueError` и перечислением отсутствующих полей. Неполный датасет не пытаются исправить автоматически.

### 3.3. Логические значения

Столбцы `needs_review` и `target_leakage` приводятся из прочитанного CSV к типу `bool`.

Принимаются только строки `true` и `false` без учёта регистра и окружающих пробелов. Значения вроде `1`, `0`, `yes`, пустой строки или `NaN` приводят к ошибке.

Это помогает не принимать некорректную разметку за отсутствие проблемы.

### 3.4. Другие модули

Используются:

- `pandas` - чтение, фильтрация и сохранение таблиц;
- `pathlib` - работа с путями;
- `math` - расчёт позиции процентиля;
- `src/common/annotate_dataset.py` - создание исходного размеченного файла при его отсутствии;
- `src/common/dataset_versioning.py` - SHA256 и версионные копии.

## 4. Порядок выполнения

Функция `main()` запускает операции в фиксированной последовательности:

1. Загружает `annotated_dataset.csv` и проверяет структуру.
2. Вычисляет SHA256 входного файла.
3. Отбирает записи, допустимые по текущим правилам.
4. Оставляет одного представителя каждой отмеченной группы дубликатов.
5. Вычисляет P5 длины оставшихся описаний и отделяет подозрительно короткие записи.
6. Оставляет предусмотренные 8 полей в каждой выходной таблице.
7. Сохраняет два CSV и их версионные копии.
8. Печатает статистику обработки.

**Порядок важен:** P5 считается не по всем исходным записям, а только после фильтрации и выбора представителей дубликатов.

## 5. Первичная фильтрация записей

Функция:

```python
filter_eligible_rows(dataset)
```

оставляет запись тогда и только тогда, когда одновременно выполнены **все четыре условия**:

1. `description` не пустое;
2. `bethesda` содержит **ровно одну** из категорий `I`, `II`, `III`, `IV`, `V`, `VI`;
3. `needs_review == False`;
4. `target_leakage == False`.

Условие отбора в коде эквивалентно:

```python
eligible_mask = (
    ~missing_description
    & valid_bethesda
    & ~needs_review
    & ~target_leakage
)
```

### 5.1. Отсутствующее описание

Исключаются значения `NaN`, пустые строки и строки, состоящие только из пробелов.

Причина: основным текстом для обучения классификатора и текущего поиска является `description`. Без описания нельзя сформировать текстовый объект обычным способом.

Такие записи **не удаляются из `annotated_dataset.csv`** и остаются доступными для ручного анализа.

### 5.2. Отсутствующая или неоднозначная Bethesda

Допустимые значения после удаления пробелов по краям:

```text
I
II
III
IV
V
VI
```

Примеры недопустимых значений:

```text
пусто
II, IV
Bethesda II
VII
```

`Bethesda II` в этом столбце не принимается, поскольку поле `bethesda` должно уже содержать результат извлечения категории, а не исходную формулировку заключения.

При нескольких категориях скрипт **не выбирает одну самостоятельно**. Запись не попадает в рабочий датасет до разрешения неоднозначности.

### 5.3. `needs_review=True`

На предыдущем этапе этот флаг означает, что обнаружена хотя бы одна причина для ручной проверки. Например:

- `missing_description`;
- `bethesda_not_found`;
- `multiple_bethesda`;
- `target_leakage`;
- `description_in_conclusion`.

`prepare_dataset.py` **не анализирует заново** значения `review_reason`. Он использует готовое значение `needs_review` из master-датасета.

### 5.4. `target_leakage=True`

Если в `description` найдено прямое обозначение Bethesda, запись исключается из рабочего датасета до проверки.

Это предотвращает обучение классификатора на тексте, который потенциально уже содержит правильный ответ.

Исходный `description` не редактируется. Скрипт **не вырезает** слова `Bethesda`, категорию или окружающий текст.

### 5.5. Почему суммы причин исключения не складываются

Одна запись может одновременно:

- не иметь `description`;
- не иметь распознанной Bethesda;
- иметь `needs_review=True`.

Поэтому количества в отдельных категориях **пересекаются**.

В терминале выводятся как отдельные диагностические показатели, так и:

```text
unique rows excluded in total
```

Это число различных строк, не прошедших хотя бы одно условие. Его нельзя получать простым сложением всех строк статистики.

### 5.6. Куда попадают исключённые записи

Строки, отклонённые на этапе первичной фильтрации, **не записываются ни в `prepared_dataset.csv`, ни в `short_descriptions_review.csv`**.

Они остаются только в полном `annotated_dataset.csv`, где можно посмотреть `needs_review`, `review_reason`, `source_table` и `source_row`.

## 6. Обработка дубликатов

Функция:

```python
select_duplicate_representatives(dataset)
```

выполняется **после** первичной фильтрации.

### 6.1. Откуда берутся группы

В `annotate_dataset.py` группы дубликатов создаются по паре:

```text
normalize(description) + normalize(conclusion)
```

Разметка сохраняется в двух полях:

| Поле | Значение |
|---|---|
| `duplicate_group` | Идентификатор вида `DUP_000001` |
| `duplicate_type` | `technical` либо `text` |

`technical` означает буквальное совпадение исходной пары во всей группе; `text` означает, что хотя бы один вариант внутри группы отличается исходным написанием, но совпадает после технической нормализации.

**`prepare_dataset.py` не вычисляет группы повторно.** Он использует значения `duplicate_group`, уже рассчитанные при аннотировании.

### 6.2. Как выбирается представитель

Для каждой непустой группы `duplicate_group` остаётся только **первая по текущему порядку строк запись, прошедшая фильтрацию**.

Пример:

| `case_id` | `duplicate_group` | Прошла первичную фильтрацию? |
|---|---|---|
| `T1_000100` | `DUP_000017` | Нет |
| `T1_004500` | `DUP_000017` | Да |
| `T2_000230` | `DUP_000017` | Да |

Результат: остаётся `T1_004500`, а `T2_000230` не выбирается. Первая запись исходной группы (`T1_000100`) уже была исключена по другой причине.

Для строк без `duplicate_group` дополнительная дедупликация **не выполняется**: такие строки сохраняются по отдельности.

### 6.3. Какие данные сохраняются

У выбранного представителя сохраняются исходные:

- `case_id`;
- `source_table`;
- `source_row`;
- `description`;
- `conclusion`;
- `bethesda`;
- `duplicate_group`;
- `duplicate_type`.

`case_id` не пересоздаётся, а ссылки на Excel-строки не меняются. `duplicate_group` также сохраняется, чтобы можно было найти другие записи той же группы в `annotated_dataset.csv`.

### 6.4. Что происходит с невыбранными дубликатами

Они исключаются из обоих выходных CSV и остаются доступными в `annotated_dataset.csv`.

В терминале печатается:

```text
Duplicate rows not selected: ...
```

Это число строк, отклонённых **на этапе выбора представителей**, а не число всех совпадений в исходных таблицах.

### 6.5. Важное ограничение для train/test

Группы дубликатов основаны на **совпадении пары** `description + conclusion`, а не только `description`.

Пример:

| `description` | `conclusion` | `duplicate_group` |
|---|---|---|
| `Описание A` | `Bethesda II` | пусто |
| `Описание A` | `Bethesda III` | пусто |

Такие записи могут остаться обеими, поскольку заключения разные. Однако **одинаковые нормализованные `description` не должны оказываться одновременно в train и test**.

Поэтому на этапе обучения нужен отдельный контроль совпадающих описаний, даже если `prepare_dataset.py` уже выполнил свою дедупликацию. При наличии `patient_id` дополнительно требуется исключить пересечение пациентов между выборками.

## 7. Проверка слишком коротких описаний: правило P5

Функции:

```python
p5(lengths)
split_short_descriptions(dataset)
```

Этот этап выполняется **после первичной фильтрации и дедупликации**.

### 7.1. Зачем проверяется длина

Короткое `description` иногда может содержать недостаточно цитологических сведений для построения текстовых признаков. Однако **сам по себе небольшой размер текста не доказывает ошибку**.

Поэтому скрипт не удаляет такие записи безвозвратно, а направляет часть из них в отдельный CSV для проверки.

### 7.2. Расчёт P5

Для каждого оставшегося `description` вычисляется:

```python
len(description)
```

Это **количество символов** в строке Python, а не число слов или токенов. Пробелы и знаки пунктуации также учитываются.

Далее длины сортируются по возрастанию. Порогом становится **5-й процентиль по методу nearest rank**:

```python
nearest_rank = math.ceil(0.05 * N)
threshold = sorted_lengths[nearest_rank - 1]
```

где `N` - количество описаний после предыдущих этапов.

Например, при `N = 40` позиция порога равна `ceil(0.05 * 40) = 2`. В качестве `P5` берётся **вторая** длина в отсортированном списке.

Важно: при одинаковом исходном содержимом и порядке данных это правило воспроизводимо. Порог **не задан константой**: он зависит от текущего датасета.

### 7.3. Когда описание направляется на проверку

Оба условия должны выполняться одновременно:

1. длина `description` **строго меньше** P5;
2. текст **не содержит ни одного** распознаваемого маркера.

В текущей версии используются маркеры:

```python
RECOGNIZED_DESCRIPTION_MARKERS = (
    "в мазке",
    "пунктирован",
)
```

При поиске маркеров регистр игнорируется. Сами маркеры проверяются как вхождения подстрок; отдельная медицинская интерпретация при этом не выполняется.

Условие записано в коде так:

```python
short_for_review = (
    (description_lengths < threshold)
    & ~has_recognized_marker
)
```

### 7.4. Примеры

Предположим, рассчитан порог `P5 = 30` символов.

| Пример | Длина | Содержит маркер? | Результат |
|---|---:|---|---|
| Очень короткое описание без маркера | 18 | Нет | `short_descriptions_review.csv` |
| Короткое описание с фразой «в мазке» | 18 | Да | `prepared_dataset.csv` |
| Описание длиной ровно 30 символов | 30 | Неважно | `prepared_dataset.csv` |
| Развёрнутое описание | 120 | Неважно | `prepared_dataset.csv` |

Числа в примере условные, не являются фактическими результатами запуска на медицинских данных.

Правило использует **`< threshold`**, а не `<= threshold`.

### 7.5. Если после фильтрации не осталось строк

`p5()` возвращает `None`. В этом случае:

- порог P5 отсутствует;
- основной результат остаётся пустым;
- файл с короткими описаниями также пуст;
- оба CSV всё равно сохраняются с заголовками.

### 7.6. Почему второй CSV - не «все записи для проверки»

`short_descriptions_review.csv` содержит **только записи, прошедшие первичную фильтрацию и дедупликацию, но отклонённые именно правилом P5**.

Туда **не попадают** строки, уже исключённые из-за:

- отсутствующего `description`;
- отсутствующей или множественной Bethesda;
- `needs_review=True`;
- `target_leakage=True`;
- невыбора из duplicate-группы.

Именно поэтому название `short_descriptions_review.csv` точнее прежнего общего названия файла «на проверку».

## 8. Выходные файлы и их структура

### 8.1. `prepared_dataset.csv`

Путь:

```text
data/processed/prepared_dataset.csv
```

Содержит записи, которые:

- прошли четыре условия первичной фильтрации;
- были выбраны при обработке duplicate-групп;
- не были направлены на проверку по правилу P5.

Это **подготовленный рабочий датасет**, а не итоговые разбиения train/test.

### 8.2. `short_descriptions_review.csv`

Путь:

```text
data/processed/short_descriptions_review.csv
```

Содержит описания, отобранные для ручной проверки из-за малой длины и отсутствия распознаваемых маркеров. Скрипт **не возвращает автоматически** такие записи в `prepared_dataset.csv` после просмотра: решение об их дальнейшем использовании и соответствующие изменения процесса нужно выполнить отдельно.

### 8.3. Общие поля двух таблиц

Оба файла имеют **одинаковые 8 столбцов в фиксированном порядке**:

| № | Поле | Назначение |
|---:|---|---|
| 1 | `case_id` | Идентификатор исходной записи |
| 2 | `source_table` | Имя исходного Excel-файла |
| 3 | `source_row` | Номер исходной строки Excel |
| 4 | `description` | Цитологическое описание |
| 5 | `conclusion` | Исходное заключение |
| 6 | `bethesda` | Одна извлечённая категория Bethesda |
| 7 | `duplicate_group` | Группа совпадающих пар «описание + заключение», если есть |
| 8 | `duplicate_type` | Тип такой группы: `technical` или `text`, если есть |

Служебные поля из master-датасета, например `needs_review`, `review_reason`, `target_leakage`, `description_in_conclusion`, **не сохраняются в выходных файлах**. Если они нужны для аудита, следует обращаться к `annotated_dataset.csv` по `case_id`.

### 8.4. Связь с оригинальными Excel

Пример соответствия:

```text
case_id       source_table            source_row
T1_000001     cytology_data_1.xlsx   10
T1_000127     cytology_data_1.xlsx   136
T2_000001     cytology_data_2.xlsx   7
```

Если запись прошла подготовку, её идентификатор и происхождение не изменяются. Для проверки `T1_000127` нужно открыть `cytology_data_1.xlsx` и перейти к **Excel-строке 136**.

Эта связь сохраняется даже после отбора и исключения части строк. Пропуски в последовательности `case_id` в подготовленном датасете являются нормальными.

**Идентификаторы и источники предназначены для внутренней трассировки.** Их не нужно показывать пользователю в результатах функции семантического поиска.

### 8.5. Формат CSV

Оба выходных файла сохраняются с настройками:

```python
sep=";"
index=False
encoding="utf-8-sig"
```

Это означает:

- разделитель столбцов - точка с запятой;
- индекс `pandas` не становится отдельным столбцом;
- используется UTF-8 с BOM для удобства открытия в табличных редакторах.

Для чтения необходимо явно передать разделитель:

```python
import pandas as pd

prepared = pd.read_csv(
    "data/processed/prepared_dataset.csv",
    sep=";",
    encoding="utf-8-sig",
)
```

**Обратите внимание:** исходный `annotated_dataset.csv` текущая версия `annotate_dataset.py` сохраняет с разделителем по умолчанию (запятая), тогда как `prepare_dataset.py` сохраняет оба результата с `;`. Это две разные настройки чтения CSV.

## 9. Версионирование с SHA256

После сохранения каждого выходного CSV вызывается функция:

```python
save_dataset_version(path)
```

из модуля:

```text
src/common/dataset_versioning.py
```

Также перед началом подготовки вычисляется SHA256 входного `annotated_dataset.csv`:

```python
source_hash = calculate_sha256(ANNOTATED_DATA_PATH)
```

### 9.1. Какие версии сохраняются

В рамках принятой схемы версионирования рядом с текущими файлами создаются отдельные версии в:

```text
data/processed/versions/
```

Ожидаемые имена при использовании существующего механизма суффикса из 12 символов SHA256:

```text
prepared_dataset_<12 символов SHA256>.csv
short_descriptions_review_<12 символов SHA256>.csv
```

Например, условные имена:

```text
prepared_dataset_63d2f4b7e2a1.csv
short_descriptions_review_1ab3cd7e9840.csv
```

Полное имя и путь каждой фактически созданной версии печатаются в терминале. За правилами хранения версий отвечает **`dataset_versioning.py`**, а не отдельный скрипт с названием `*_SHA256.py`.

### 9.2. Какие хеши фиксируются

В отчёте о выполнении отображаются:

- SHA256 входного `annotated_dataset.csv`;
- SHA256 выходного `prepared_dataset.csv`;
- SHA256 `short_descriptions_review.csv`;
- пути к версионным копиям обоих выходных файлов.

Каждый SHA256 относится к **байтам конкретного файла**. Изменение хотя бы одного байта приводит к другому хешу; одно лишь переименование файла без изменения содержимого не меняет его SHA256.

При логировании экспериментов в MLflow версию используемого **для обучения или поиска** датасета нужно фиксировать по его полному SHA256. Полезно дополнительно сохранять хеш входного master-датасета и Git commit SHA, чтобы можно было восстановить происхождение результата.

**Важное разграничение:** `prepare_dataset.py` вычисляет хеши и сохраняет CSV, но **не создаёт MLflow run автоматически**. Регистрация MLflow выполняется кодом соответствующего эксперимента.

## 10. Статистика выполнения

После выполнения выводятся следующие показатели:

| Показатель в терминале | Что означает |
|---|---|
| `Rows in annotated_dataset` | Количество строк на входе |
| `annotated_dataset SHA256` | Полный хеш входного файла |
| `missing description` | Сколько записей имеют пустое описание |
| `invalid or multiple Bethesda` | Сколько записей не имеют ровно одной категории I-VI |
| `target leakage` | Сколько записей имеют `target_leakage=True` |
| `needs review` | Сколько записей имеют `needs_review=True` |
| `unique rows excluded in total` | Сколько разных записей исключено первичной фильтрацией |
| `Eligible rows before duplicate selection` | Сколько строк прошло первичную фильтрацию |
| `Duplicate rows not selected` | Сколько строк отброшено при выборе представителей групп |
| `P5 description length` | Рассчитанный порог длины или `not available` |
| `Rows in prepared_dataset.csv` | Сколько строк в основном результате |
| `Rows in short_descriptions_review.csv` | Сколько строк направлено на проверку по P5 |
| `... SHA256`, `... version` | Хеши и пути сохранённых версий |

Числа зависят от содержимого конкретной версии `annotated_dataset.csv`; в инструкции они намеренно не зафиксированы.

### 10.1. Проверка баланса строк

При каждом запуске должны выполняться соотношения:

```text
исходные строки
    = исключённые на первичной фильтрации
    + прошедшие первичную фильтрацию

прошедшие первичную фильтрацию
    = невыбранные дубликаты
    + строки после дедупликации

строки после дедупликации
    = prepared_dataset.csv
    + short_descriptions_review.csv
```

Эти соотношения удобны для контроля потерь записей между этапами. Отклонённые строки не исчезают из исходного master-датасета.

## 11. Использование в задачах диплома

### 11.1. Классификация Bethesda

Для задачи классификации:

- **вход модели - только `description`**;
- `bethesda` - целевая категория;
- `conclusion` не включается в признаки, поскольку именно из него извлекалась целевая категория;
- `case_id`, `source_table`, `source_row` и сведения о дубликатах не являются текстовыми признаками;
- `prepare_dataset.py` не создаёт train/test и не обеспечивает автоматически отсутствие утечки между ними.

Перед обучением нужно дополнительно проконтролировать совпадающие нормализованные `description` между train и test. При наличии `patient_id` нужно исключить разделение записей одного пациента между выборками.

### 11.2. Семантический поиск похожих случаев

Текущий `prepared_dataset.csv` содержит необходимые базовые сведения: описание, Bethesda и заключение. Для поиска текстом запроса и индексируемым содержимым обычно служит `description`; `bethesda` и `conclusion` могут отображаться как информация о найденном случае.

**Но текущие правила фильтрации разработаны довольно строго и ориентированы на однозначную Bethesda.** В результате из общего корпуса исключаются, например, описания без распознанной категории, даже если они могли бы быть полезными для семантического поиска.

Это **известное ограничение текущей версии**, а не доказательство непригодности таких записей для поиска. Если консультант утвердит разные критерии отбора для классификации и поиска, потребуется отдельно определить корпуса или дополнительные фильтры. В текущем документе не предполагается, что такое изменение уже выполнено.

Скрипт также не выполняет сам поиск, не строит TF-IDF/BM25 или эмбеддинги, не создаёт индекс FAISS и не оценивает Recall@K. Всё это относится к последующим этапам проекта.

## 12. Что скрипт не делает

`prepare_dataset.py`:

- не исправляет медицинские заключения и не назначает Bethesda вручную;
- не переносит описательный текст из `conclusion` в `description`;
- не удаляет исходные Excel или строки из `annotated_dataset.csv`;
- не пересчитывает разметку дубликатов по собственным правилам;
- не объединяет записи по семантическому сходству;
- не отбрасывает автоматически **все** совпадающие `description`;
- не проверяет пересечение пациентов между train и test;
- не создаёт train/test, не обучает модели и не ведёт MLflow-логирование;
- не формирует стратифицированную выборку из 50 записей для ручной проверки;
- не выполняет медицинскую валидацию подготовленного корпуса.

Эти ограничения важно учитывать при интерпретации результата и описании воспроизводимого эксперимента.

## 13. Запуск из корня репозитория

Перед запуском должны быть настроены проектное Python-окружение и зависимости (в частности, `pandas`).

**Основная команда:**

```bash
python -m src.common.prepare_dataset
```

Допускается и прямой запуск, предусмотренный в скрипте:

python src/common/prepare_dataset.py

## 14. Проверка результата

После выполнения рекомендуется проверить:

1. В терминале отсутствуют исключения, выведены три SHA256: источника и обоих результатов.
2. Созданы `prepared_dataset.csv` и `short_descriptions_review.csv`.
3. В обоих выходных файлах есть все **8 ожидаемых столбцов** и нет лишнего столбца индекса.
4. Файлы корректно читаются с `sep=";"` и `encoding="utf-8-sig"`.
5. В `prepared_dataset.csv` все `description` непустые, а `bethesda` имеют одно из шести допустимых значений.
6. Для каждой непустой `duplicate_group` в основном результате не более одного представителя.
7. В `short_descriptions_review.csv` действительно лежат записи, удовлетворяющие правилу P5 по рассчитанному порогу.
8. Все `case_id`, `source_table`, `source_row` можно сопоставить с `annotated_dataset.csv`.
9. Числа по этапам фильтрации согласуются с формулами баланса строк из раздела 10.
10. Имя и полный хеш фактически использованного датасета зафиксированы в эксперименте классификации или поиска.

Для быстрого локального просмотра:

```python
import pandas as pd

prepared = pd.read_csv(
    "data/processed/prepared_dataset.csv",
    sep=";",
    encoding="utf-8-sig",
)

review = pd.read_csv(
    "data/processed/short_descriptions_review.csv",
    sep=";",
    encoding="utf-8-sig",
)

print("Prepared:", prepared.shape)
print("Short descriptions for review:", review.shape)
print(prepared.columns.tolist())
```

## 15. Частые проблемы

### `annotated_dataset.csv` не найден

Скрипт автоматически попытается вызвать `annotate_dataset.py`. Проверьте наличие исходных Excel по путям, ожидаемым этим модулем, а также настроенное Python-окружение.

### Отсутствуют обязательные столбцы

Будет `ValueError` со списком отсутствующих полей. Убедитесь, что входной CSV создан актуальной версией `annotate_dataset.py`, а не старым скриптом с иной структурой.

### Ошибка преобразования `needs_review` или `target_leakage`

Проверьте, нет ли пропусков или значений, отличных от `True`/`False`. Не следует механически заменять неизвестные значения на `False`, потому что это может пропустить проблемную запись в рабочий корпус.

### CSV читается как один столбец

Вероятно, пропущен параметр `sep=";"` при чтении одного из выходных файлов.

### Появились неожиданные пропуски идентификаторов

После фильтрации и выбора представителей дубликатов `case_id` **не перенумеровываются**. Поэтому разрывы в нумерации нормальны и не означают, что связь с исходными файлами потеряна.

### Изменился SHA256

Проверьте, какой именно файл сравнивается и изменилось ли его содержимое, порядок строк, значения, кодировка или сериализация. Хеш чувствителен к байтам, а не только к смыслу данных.

### Основной датасет оказался меньше ожидаемого

Последовательно посмотрите показатели `unique rows excluded in total`, `Duplicate rows not selected`, количество строк в `short_descriptions_review.csv` и порог P5. Для изучения конкретных причин исключения обращайтесь к `annotated_dataset.csv`.

## 16. Принципы воспроизводимости и безопасности

- Сохраняйте в Git **скрипты и документацию**, а не исходные медицинские Excel и не производные CSV с потенциально чувствительными данными.
- Версии датасетов, самих данных и артефакты моделей храните в разрешённом защищённом месте; настройки `.gitignore` должны исключать их из публикации.
- Для каждого MLflow run сохраняйте полную версию используемого датасета, модель и её параметры, метрики, seed, Git commit SHA и другие согласованные метаданные эксперимента.
- Общие изменения критериев отбора или схемы CSV согласовывайте между участниками проекта до объединения веток.
- Сам `prepared_dataset.csv` не является медицинским заключением и не заменяет проверку врачом.
